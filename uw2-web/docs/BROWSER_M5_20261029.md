## Korean CHAR.LZW
Actual decoded LS11 chunk sizes:
- chunks 0..5: 5,120 bytes each.
- chunk 6: 15,360 bytes.

This means:
- hero 0..5: 8 frames each at 640 bytes/frame.
- final chunk: 24 frame-equivalents at 640 bytes/frame, consistent with town NPC artwork.

For each 640-byte hero frame:
- the first four 128-byte blocks independently decode as coherent 16x16 planar 4bpp color blocks.
- those four blocks reconstruct a 32x32 color frame as TL/TR/BL/BR.
- the fifth 128-byte block is a blitter mask/control block, but its exact combine semantics are NOT yet established.

Multiple hypotheses for the fifth block were tested and rejected:
- simple 32x32 1bpp row-major alpha mask,
- four quadrant alpha planes with direct polarity,
- globally permuted color/mask planes selected against a public João reference,
- grouping all image tiles first and masks after them.

The current browser therefore uses only the confirmed color layer and treats color index 0 as transparent. This is materially better than the diagnostic square, but the visible orange/brown residual pixels must not be called a final sprite decode until the fifth block is proven from code.

Firefox validation:
- save 1 loads Catalina in Tunis at the real saved town position.
- moving left changes state from facing=down, parity=0 to facing=left, parity=1.
- the 32x32 source sprite moves with the player and changes frame accordingly.
PASS for position/facing/frame integration.
Mask/control semantics remain OPEN.

## Korean sea-ship sprites
User DATA1.LZW chunk 11 is 32,768 bytes:
- first 0x4000 = 128 planar 16x16 world tiles.
- remaining 0x4000 = exactly 16 x 0x400-byte ship frames.

Each ship frame:
- 0x200 bytes packed 4bpp color, two pixels per byte.
- 0x200 bytes packed 4bpp mask.
- mask nibble 0xF = transparent.

All 16 frames render as coherent 32x32 sea ships.
The runtime uses the known 8-direction-to-4-facing table:
[0,1,1,1,2,3,3,3]
and step parity to choose animation frame.

Firefox validation:
- Danzig -> Harbor -> sail.
- actual Korean ship artwork is drawn at (286,238) instead of the yellow diagnostic square.
PASS.

## WINDCUR.DAT
Exact user file size 1,350 bytes = 3 x 450-byte pages.
Grid = 30 x 15.
At world-chip position:
- col=floor(x/72), row=floor(y/72).
Byte:
- bits 0..2 speed 0..7
- bits 3..5 direction 0..7, 0=north clockwise
- bits 6..7 weather flags

Wind page:
- Apr..Sep -> page 0
- Oct..Mar -> page 1
Current = page 2.

User save validation:
Tunis save, 1522-05-28, sea point (242,370):
- wind raw 34 -> south, speed 2.
- current raw 2 -> north, speed 2.

Danzig save, 1522-07-06, sea point (286,238):
- wind raw 29 -> southeast, speed 5.
- current raw 56 -> northwest, speed 0.

Firefox sea screen displays the Danzig values exactly.
PASS.

## Korean player fleet structures from bundled HORIEDIT
Ground truth offsets are page-relative for this Korean save format:
ship1_addr[6] = {0x2244,0x2776,0x31DA,0x3C3E,0x370C,0x2CA8}
Ship1 size = 9
Ship2 at 0x4692, size 30
Ship3 at 0x4C35, size 25
Ship5 at 0x501D, size 25
Ship4 at 0x5291, size 12

The sizes are independently supported by table-span arithmetic:
- Ship3: 0x501D - 0x4C35 = 1000 = 40 * 25.
- Ship5: 25 models * 25 bytes ends immediately before Ship4.
- Ship4: 25 models * 12 bytes ends immediately before the following port table area.

The editor's own conferm_hero() walks Ship1 until select=0xFF and verifies Ship3 model selection.
